# ADR-004 — Persistência e snapshots

Origem: UC-006–009, API-008. Estado: Proposta v1.0; decisão humana técnica pendente.

Contexto: entregar a formatação editorial solicitada sem acrescentar infraestrutura sem finalidade. Decisão candidata: SQLite para metadados/leitura; blobs imutáveis por hash em diretório de gerações; um escritor serializado; manifestos e ponteiro de geração para troca de acervo.

Alternativas e tradeoffs: JSON solto: transações e concorrência frágeis; banco remoto: contraria preferência local; copiar DB aberto para backup: snapshot pode ser inconsistente. Consequências/limites: Atomicidade SQLite não torna banco e filesystem uma transação única. Usar staging, diário de intenção e reconciliação no início; blob finalizado antes de referenciá-lo, resíduo sem referência pode ser limpo.

Critério de confirmação/refutação e retorno: Injetar falha após cada ponto de commit/troca e restaurar anterior. Backup usa exportação lógica consistente ou API de backup, nunca cópia ingênua de arquivo aberto. Validação de viabilidade será executada antes de adotar este ADR em código. Uma prova que falhe reabre este ADR e apenas UC/NUC/FLOW dependentes; não reduz controles para manter a opção preferida.
